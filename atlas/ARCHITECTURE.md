# NEO JIZO ATLAS — 独立データ基盤設計 001

設計日：2026-10-08  
状態：新規DBの**構造と合成検証**。既存 `mykeibadb` への実行・移行は未実施。

## 何を独立させるのか

JRA-VAN、NAR、過去の `mykeibadb` は引き続き「供給元」。データの保管・識別・時点管理・モデル向け編集はATLASが所有する独立契約で行う。既製ベンダーDBの物理テーブル構造をATLASの公開APIにはしない。

| 層 | 役割と保存方式 | 正式度 |
|---|---|---|
| 取得・原本 | JV-Link SDK、許諾済みNAR、ローカル既存DBの読み取り。取得単位ハッシュ・出典・許諾状態を保全 | 規約に応じたローカル限定 |
| 不変データ原本 | 大容量の調教・履歴は圧縮済みParquet/原本保管（SHA-256） | バージョン固定 |
| ATLAS統合DB | 新規 **`neo_jizo_atlas`** PostgreSQLの `atlas` スキーマ | 本リポジトリにマイグレーション定義 |
| 研究スナップショット | 現行の不変Canonical Parquetを再利用。検証後のみ世代更新 | 読取専用の版をモデルに供給 |
| FORWARD | 完全な発走前入力と予測を個別凍結、事後確定結果は別 | 未来検証、現行PR #58・#59 |

**PostgreSQLを捨てる提案ではない。ベンダー製の旧スキーマに従属するのを止める。** 新旧DBは別クラスタ・別DBの運用を前提に検討し、同じクラスタに置くかどうかはバックアップ・容量・保守状況を確認して決定する。

## 初期スキーマ

`atlas/sql/001_init.sql` は、**新しく空で作成した**専用PostgreSQL 18データベースのみに適用する提案。

| 論理区分 | DBテーブル |
|---|---|
| 出典・利用権限 | `data_source` |
| 取得バッチ・二重投入防止 | `import_object`（元ファイルSHA-256単位で一意） |
| 発見時点と版を持つ原本観測 | `raw_observation`（小さいデータならJSONB、大量データは不変のオブジェクト位置を参照） |
| 馬の内部IDと公式ID対応 | `horse`, `horse_identifier` |
| レースの内部IDと供給元ID対応 | `race`, `race_identifier` |
| レース・出走馬・結果の観測履歴 | `race_observation`, `runner_observation`, `result_observation` |
| 隔離と検証履歴 | `quarantine_issue`, `ingest_decision` |

### 旧DBと決定的に異なること

1. **JRA/NARで内部IDを統一**し、供給元固有IDとの対応は別テーブル。馬名のみ／名前と生年の推測ハッシュで同一馬扱いしない。
2. **開催前の特別登録、確定出馬表、結果**を異なる版・状態として残す。後日の上書きで発走前の記録を消さない。
3. **取得時刻、配信側時刻、レース時刻を別列**で保管する。配信側時刻が不明ならNULLであり、取得時刻を偽装して補完しない。
4. 一度投入した原本・レース観測・結果・検証判断は**UPDATE/DELETE拒否**。変更履歴は新しい観測を追加して残す。
5. 取得ファイルSHA-256と供給元IDにUNIQUEを設け、**同一ファイルの無限再投入を禁止**。異なるバージョン同士は後で比較・隔離する。
6. 規約状況がUNVERIFIEDなら原本観測テーブルへの投入自体を拒否。商用配信可否も別列で管理し、内部研究許諾と混同しない。
7. 結果不明はNULL／UNRESOLVEDとして扱う。勝率・連対率・複勝率を学習用に0補完しない。
8. **複勝・連対・調教・血統・荒れ度**を後付け特徴量として追加可能な構造。確定結果や当日オッズは発走前の能力特徴量に自動混入させない。

## 大量データとコストを抑える

数百万〜数千万の坂路・ウッド調教を1件ずつJSONBへ重複保存する必要はない。原本を圧縮Parquetやライセンス許容のローカル保管に固定し、`raw_observation` にはハッシュとロケータだけを記録できる。研究はDuckDB/Parquetを使い、PostgreSQLはID・更新の整合性・取得証拠の管理に集中する。

## 手間の少ない取り込み：次の実装ゲート

「JRA/NARの許諾済み原本を自動取得、あるいは指定フォルダーへ置く → ハッシュで新規分だけ検知 → データ契約に沿って検証 → 不正・曖昧データは隔離 → 合格分だけ新しいCanonical版を生成」。日時・行数・追加・重複・隔離のレポートを日本語で表示。失敗したバッチは後から再処理可能な台帳を残す。

このミッションでは**自動取得・自動投入は未実装**。公式SDKのレコード種別と更新提供時刻、権利条件が確認されるまではハードコードした取り込みをしない。

## 実行禁止事項

- `mykeibadb`に`atlas/sql/001_init.sql`を実行しない。
- 旧DBの再初期化、移動、削除、復旧、サービス起動を自動実行しない。
- GitHubには馬単位の実データ、JV-Linkの取得原本、契約キー、DBダンプをアップロードしない。
- 商用配布は通常のData Lab.契約だけでは許可されず別途利用権利の確認が必要。
- ドライバー、権利、監査、物理バックアップ、実DBの検証が揃わないうちは研究から本番へ自動昇格しない。

## CI

GitHub Actionsは**使い捨てPostgreSQL 18**を起動し、同じマイグレーションを2回適用して再実行性を確認。そのあと合成レコードで許諾・重複・ID・結果欠損・履歴上書き拒否を検査し、トランザクションでロールバックする。

このCIは**新スキーマの技術検証**であり、停止中の`mykeibadb`の正常性・既存データ完全性・モデル精度を証明するものではない。
