# NEO JIZO ATLAS — Windows運用メニュー（ATLAS-MENU-001）

2026-10-08：GitHubブランチ上に実装。ユーザーのWindows実機へインストール済みという意味ではありません。

## 使い方（安全な順番）

コードを承認済みの作業フォルダーへ安全に同期し、`tools/ATLAS-MENU.cmd`を**ダブルクリック**します。

| キー | 操作 | 既存DBを変更 | JRA-VAN通信 |
|---|---|---|---|
| **1** | ATLAS-DOCTOR：OS/Python/新DB診断 | しない | しない |
| **2** | ATLAS-OFFLINE-SELFTEST：合成テスト7組を実行 | しない | しない |
| **3** | ATLAS-JRA-COM-CHECK：ローカルCOM登録診断 | しない | しない |
| **4** | ATLAS-DB-CHECK：新DB事前確認 | しない | しない |
| **5** | ATLAS-DB-CREATE：`CREATE`と明示入力後、新DB作成 | **新`neo_jizo_atlas`だけ** | しない |
| **6** | 初回JRA-VAN通常差分取得 | DBはしない | **する** |
| **7** | JRA受信→新DB RAW→正規化 | **新DBだけ** | **する** |
| **8** | 7番を1時間ごとに実行 | **新DBだけ** | **する** |
| Q | 終了 | しない | しない |

**1→2→3→4**までが安全な初回手順。5～8は契約内容・Windows SDK・接続情報・ソース利用許可を検証し、必要な初期設定を終えてから実行します。現時点ではGitHub上でのコードと合成試験に基づく設計であり、実機のJV-Link通信は未実施です。

### 原則

- ボタン/キーを押さない限り**何も取り込まない**。Windowsの起動時実行設定、サービス登録、既存フォルダー移動、旧DB削除は行わない。
- 合成テストでは`ATLAS_PG_DSN`、`ATLAS_PG_ADMIN_DSN`、秘密情報、実DB接続フラグを子プロセスから**除外**する。GitHubが不調でもローカル環境で基本動作を確認できるが、実DB統合テストの代わりではない。
- COM確認は`JVDTLab.JVLink`生成/破棄のみ。`JVInit`、`JVOpen`、`JVGets`を呼ばず通信しない。実データ取得許諾やSDKの正常動作を証明するものではない。
- 専用DB作成は一度きり。既存`mykeibadb`にはSQLを書かない。既存`neo_jizo_atlas`の未知の内容も変更せずBLOCKEDとする。
- 「初回取得」は通常差分のみ。過去15年の全量取得やNAR自動取得は**まだできない**。JRAのRA/SE以外の全項目正規化も未実装。
- 操作で失敗した場合はBLOCKED表示とし、キーや接続URLをチャット・GitHubに貼らない。
- UIはUTF-8の日本語を表示するため、メニューの冒頭でWindowsコンソール文字コードを65001へ設定している。

## GitHub CIについて

PR #65では`BuildFailed` /`startup_failure` / **0 jobs**により最新コードのGitHubテストが未実行。`docs/ATLAS_CI_INCIDENT_20261008.md`を参照。メール認証状態が関与している可能性はありますが原因未確定。**このメニューを作ったことはCI復旧や本番稼働の証明ではありません。**

最終受入判定は、①安全なWindows診断、②実機SDK現物照合、③新DB作成、④公式JRA原本の最初の1レースが安全に登録されること、⑤再実行時に重複しないこと、⑥旧DBが不変であることです。
